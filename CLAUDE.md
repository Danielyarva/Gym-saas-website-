# AI Coach OS

Fitness/transformation coaching SaaS. Coaches manage clients, workout/nutrition plans, and check-ins; clients track progress and use an AI chat coach. Full spec: `docs/PRD.md`.

## Current phase

Phase 1 complete — authentication, coach dashboard, client management, client profile (PRD §7–10, §36) are implemented on both frontend and backend, code-reviewed, and verified end-to-end in a real browser (desktop + mobile).

Phase 2 complete — client account invites, onboarding, the exercise library, workout plan builder, nutrition plan builder, daily check-ins, and the client app shell (PRD §11–14) are implemented on both frontend and backend, code-reviewed, and verified end-to-end in a real browser (desktop + mobile). Along the way, fixed two role-handling gaps Phase 1 never needed: `(dashboard)/layout.tsx` had no role gate, and `/login` always redirected to `/dashboard` regardless of role.

Phase 3 complete — progress charts (weight, body measurements, steps, sleep, workout/nutrition adherence) with a time-range selector, progress photos with before/after comparison, and periodic body-measurement logging via the daily check-in (PRD §15) are implemented on both frontend and backend, code-reviewed, and verified end-to-end in a real browser (desktop + mobile). `CoachClient.adherencePct`/`progressPct` — dead/always-null since Phase 1 — now get recomputed on every check-in submit, so the Overview and dashboard "Adherence"/"Average Progress" stats are real for the first time. No AI-generated weekly report (that's Phase 4's PRD §19 narrative version); the Weekly chart range plus check-in history already cover the same ground without AI.

Phase 4 complete — AI Coach chat, automatic post-check-in risk analysis, and coach-triggered weekly reports (PRD §16–19, §29–30) are implemented on both frontend and backend, code-reviewed, and verified end-to-end in a real browser (desktop + mobile). Every AI call goes through one `aiService` wrapper (Anthropic behind an `AIProvider` interface, structured output via forced tool-use, Zod-revalidated) that degrades to a clean `AI_NOT_CONFIGURED` (503) with a usage-log row whenever no `ANTHROPIC_API_KEY` is set — true throughout this sandbox, so the phase never exercised a real model response; add a key later and nothing else changes. Risk detection (§18) lives inside the same `AiInsight` row as progress analysis (§17), not a separate pipeline. Weekly reports are coach-triggered (no job queue until Phase 7), with only the narrative from AI — all metrics computed deterministically from existing check-in data.

Phase 5 complete — coach-client messaging (conversations, read/unread, a polling-based typing indicator, image attachments) and a notification center (PRD §20–21) are implemented on both frontend and backend, code-reviewed, and verified end-to-end in a real browser (desktop + mobile). Messages are a flat `Message` table keyed by `clientId` — no `Conversation` wrapper, since a coach has exactly one client per relationship. Both roles read and write the same thread for the first time in this app (`requireClientOwnershipOrSelf()` now gates a POST, not just reads). Typing indicators use two ephemeral timestamp columns on `CoachClient`, polled via REST per PRD's explicit "no WebSockets yet." Notifications fire for check-ins, missed workouts, AI at-risk analysis (RED only), weekly reports, and new messages, with email sent only for the two urgent types (new message, at-risk). Along the way, relabeled Phase 4's per-client "Chat" tab to "AI Coach" to disambiguate it from this phase's new "Messages" tab, and discovered mid-build that Next.js route groups don't namespace URLs — the client app's Messages/Notifications pages live at `/inbox` and `/alerts` rather than colliding with the coach's `/messages` and `/notifications`.

Phase 6 complete — subscriptions and payments (PRD §24) are implemented on both frontend and backend, code-reviewed, and verified end-to-end in a real browser (desktop + mobile). Plan limits (Starter 5 / Pro 25 / Business 75 clients) live in one typed config module (`backend/src/config/plan-limits.ts`), never hardcoded elsewhere, and are enforced in exactly one place (`clientsService.create`). Razorpay checkout ships behind a real `PaymentProvider` abstraction (so Stripe can be added later without touching call sites) that degrades to a clean `BILLING_NOT_CONFIGURED` (503) with no `RAZORPAY_KEY_ID`/`SECRET` set — true throughout this sandbox, so the phase never exercised a real checkout. Payments are one-time 30-day period purchases, not Razorpay's recurring Subscriptions API — no auto-renewal until Phase 7's job queue exists; a lapsed paid plan is lazily self-healed back to Starter on read instead. Activation is idempotent across a race between the client's post-checkout `/verify` call and the `/webhook` fallback, via an atomic conditional update rather than a read-then-write check. The `SUBSCRIPTION` notification type (defined but unused since Phase 5) finally fires.

Phase 7 complete — Redis-backed background jobs and web push notifications (PRD §28, §21) are implemented on both frontend and backend, code-reviewed, and verified end-to-end in a real browser (desktop + mobile). Unlike AI/Razorpay, `REDIS_URL` is required infrastructure, not a gracefully-degrading third-party key — six BullMQ queues (`emailQueue`, `aiAnalysisQueue`, `webhooksQueue`, `pushQueue`, `weeklyReportQueue`, `reminderQueue`) run against it, with a real in-process `Worker` per queue in both `src/worker.ts` (dev/prod entrypoint) and the Jest suite (`tests/setup.ts`, against a separate Redis logical DB). Only the emails/triggers that can tolerate arriving a beat later moved to queues (at-risk/new-message/payment-receipt emails, AI check-in analysis, Razorpay webhook event processing); verification emails, password resets, and client invites stay direct fire-and-forget since coaches/clients expect those instantly and several existing tests read the invite token synchronously. Two new repeatable jobs exist for the first time: a Monday weekly-report fan-out (finally satisfying PRD §19's "every week generate", deferred since Phase 4) and a daily check-in reminder sweep (the first real trigger for the previously-dead `SYSTEM` notification type). Web push ships genuinely functional in this sandbox — VAPID keys are self-generated, no external paid account needed — via a `PushSubscription` table, a `pushService` wrapper that gracefully no-ops without VAPID keys, and a "Enable push notifications" opt-in card on both the coach's `/notifications` and the client's `/alerts` pages. Real end-to-end verification caught and fixed a genuine bug: `usePushSubscriptionStatus` originally awaited `navigator.serviceWorker.ready`, which never resolves until a service worker is registered, leaving the opt-in card stuck pending forever; fixed to use `getRegistration()` instead. The one piece unverifiable from this sandbox is the browser's own real Push API registration against Google's push service (no outbound network path for raw browser traffic here) — the subscribe flow reaches that real call and fails there with a clean, user-visible toast, exactly the boundary PRD's own scope expects.

Phase 8 complete — analytics, an admin panel, and targeted performance work (PRD §31, §36) are implemented on both frontend and backend, code-reviewed, and verified end-to-end in a real browser (desktop + mobile). This is the final phase in PRD §36's roadmap. The `ADMIN` role and a seed-only admin account had existed unused since Phase 1 — logging in as one previously hit a genuine infinite redirect loop (`/dashboard` → wrong-role → `/today` → wrong-role → `/dashboard`); fixed with a real `/admin` destination and updated role-gates on all three app shells. Nine PRD-named SaaS metrics (new/active coaches, active clients, weekly active users, check-in rate, AI usage, subscription conversion, churn, client retention) are computed platform-wide in a new, deliberately unscoped `admin-analytics` repository/service — the first cross-coach queries in the codebase, everywhere else is coach-scoped by design. Churn specifically recomputes an "effective" status rather than trusting `Subscription.status` directly, since `ensureCurrent` (Phase 6) only flips a lapsed plan to `CANCELED` lazily on that coach's next request, not via a sweep. "Performance optimization" was scoped to exactly what these new queries need: five targeted DB indexes and a 5-minute Redis cache around the analytics aggregate (`jobs/connection.ts`'s shared connection, its first non-BullMQ use) — not a broader audit of Phases 1-7. Code review caught that the redirect-loop fix only covered the login-page entry point, leaving the loop reachable via a direct URL or old bookmark; fixed by giving every role-gate a real per-role home instead of a hardcoded fallback.

## Working process

- Read only the PRD sections relevant to the current phase before starting — not the whole file.
- Start each phase in plan mode. Wait for explicit approval on the plan before writing code.
- Follow PRD §41's per-phase checklist: explain what's being built → create files → complete code → where each file belongs → install commands → migration commands → test instructions → verify integration with the previous phase.
- The app must stay runnable after every phase — no half-wired features left broken.
- When a phase is done: commit, then run the diff through the code-reviewer subagent before starting the next phase.

## Stack

- Frontend: Next.js, TypeScript, Tailwind, shadcn/ui, Zustand, TanStack Query, Recharts (PRD §4)
- Backend: Node.js, Express, TypeScript, Prisma, PostgreSQL — controller → service → repository, no business logic in routes (PRD §5)
- AI: Claude via Anthropic API, behind the AIProvider abstraction (PRD §29)

## Conventions

- No `any`. Zod schemas for all runtime validation — request bodies and AI output alike.
- No hardcoded plan limits, API URLs, or secrets — config/env only.
- A coach can only ever access their own clients. This is a security invariant, not just a feature — test it explicitly (PRD §32).
- Every new screen needs loading, empty, and error states (PRD §38).
